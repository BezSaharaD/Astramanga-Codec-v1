# MangaVQ / `.astra` — кастомный кодек изображений для манги и манхвы

## Зачем он вообще нужен

Обычные форматы (WebP и т.п.) — универсальные: они умеют кодировать любую картинку и платят за эту универсальность весом. У сканов манги/манхвы контент специфичен (полутоновый скринтон, чёрно-белые заливки, чистые линии, текст в баблах). Специализация под этот домен позволяет одновременно достичь трёх целей, которые для универсального кодека обычно несовместимы:

- **Вес не хуже WebP** (в среднем ощутимо меньше).
- **Ноль работы CPU на декоде одного пикселя**: вся реконструкция картинки выполняется **GPU-шейдером** параллельно по всем пикселям сразу, без последовательного прохода по изображению. Это архитектурное требование читалки, не пожелание.
- **Random access**: можно декодировать произвольный кусок страницы (например, только видимую полосу), не разворачивая всё изображение целиком — чего WebP не умеет в принципе.

---

## Как устроено кодирование

Страница режется на блоки (в основном **4×4** и **8×8** пикселей). Для каждого блока энкодер выбирает один из нескольких способов его представить — тот, что даёт лучшее качество на единицу веса для конкретного содержимого блока.

Декодирование всех блоков идёт **в два прохода**:

1. В первом параллельно рендерятся «базовые» независимые представления.
2. Во втором — представления, которые могут ссылаться на уже восстановленные соседние блоки (например, копия со сдвигом).

Эта **двухпроходная схема** — ключевой трюк: она позволяет использовать техники, обычно требующие последовательного декодирования (predictive coding, copy-from-neighbor), но **не ломает GPU-параллельность**. Каждый проход целиком параллелен; проходов просто два, а не один.

## Технологии реконструкции блока — что взято

- **Solid** — блок одного сплошного цвета: самый дешёвый режим для однотонных заливок (чёрные панели, белый фон).
- **Planar** — блок как плоскость (линейный наклон яркости): дёшево и без ступенек описывает гладкие градиенты.
- **DCT (частотное представление)** — применяется на скринтоне. Скринтон — периодическая точечная структура, и в частотной области она сворачивается в несколько компактных коэффициентов, тогда как поблочный поиск похожего образца (VQ) вынужден мириться с рассинхроном по фазе/шагу точек.  
  Для манги отдельно настроен более мелкий базис (**4×4 вместо 8×8**) там, где это даёт выигрыш без раздувания остатка — но это ограниченная область применения: изолированный выигрыш от более мелкого базиса на практике съедается тем, что соседние блоки предсказывают уже от другой реконструкции.
- **Coverage (покрытие чернил)** — специальный режим для «чернила на белой бумаге» (текст, обводки, баблы): вместо полноценного кодирования пикселей хранится грубая (**3-битная**) карта покрытия, фон = белый. Работает только для манги (у манхвы «белый» фона обычно не такой чистый).
- **VQ (векторное квантование через частотный словарь)** — блок заменяется индексом ближайшего образца в общем для главы словаре. Словарь строится не кластеризацией (k-means), а как **топ самых частых реальных блоков** — это дешевле и даёт более точное совпадение, поскольку кластеризация усредняет блоки в размытые центроиды.
- **IBC (intra block-copy)** — блок описывается как копия уже реконструированной части кадра со сдвигом (аналог motion-compensation в видеокодеках, только внутри одного кадра). Из-за двухпроходной схемы остаётся полностью GPU-параллельным.
- **Intra-предсказание (V/H/DC/diagonal)** — предсказание блока от уже восстановленных соседей по нескольким фиксированным направлениям, тоже во втором проходе.
- **pl8 (planar + квантованный остаток)** — специально для мягкой закраски и зерна манхвы: плоскость плюс поправка поверх неё.
- **Адаптивное квантование остатка по классам содержимого**:
  - на резких краях остаток квантуется тонко;
  - на скринтоне и «занятых» текстурных зонах — грубо (шум маскирует огрубление);
  - на зерне — отдельный, промежуточный класс (иначе зерно либо теряется, либо стоит неоправданно дорого).

## Хрома

Цвет хранится отдельно от яркости:

- в пониженном разрешении (в несколько раз грубее люмы),
- с последующим DCT поверх этого грубого плана,
- с перцептивным квантованием (низкие частоты точнее, высокие — грубее),
- и «мёртвой зоной»: мелкие DCT-коэффициенты, которые всё равно являются шумом, обнуляются целиком — это почти не портит картинку, но заметно режет вес.

Уровень квантования подобран так, чтобы избежать характерного дефекта — «протекания» цвета через границу объекта на соседний (если квантовать слишком грубо, цвет одного объекта размазывается на соседний по 16-пиксельным блокам).

Апсемплинг цвета до полного разрешения делается по направляющей (guided) схеме: веса интерполяции берутся из уже реконструированной яркости, чтобы цветные ореолы не появлялись на резких границах.

## Фильтры на стороне декодера (бесплатные, ничего не хранится в файле)

Отдельный класс техник — не влияет на вес, применяется как проход шейдера при декодировании:

- **Deblock** — узкий фильтр, сглаживающий швы между блоками (в духе loop-filter из WebP/H.264/AV1).
- **Anti-band** — точечное размытие только там, где на регулярной сетке границ блоков есть маленькая ступенька (banding), не трогая настоящие резкие края.
- **Защита линий по структурному тензору** — отличает настоящую линию (сильный градиент поперёк, слабый вдоль) от квантового шума (градиент во все стороны одинаковый) по форме градиента, а не по его амплитуде. Это позволяет не потерять даже низкоконтрастные линии (тёмный волос на тёмной коже), которые обычный порог по яркости бы пропустил.
- **VP8-класса адаптивный loop-filter** — решает системную проблему: разные блоки одного гладкого градиента иногда кодируются разными представлениями (плоскость/копия/словарь/заливка), и на границах между ними возникает едва заметная, но регулярная решётка швов, даже когда усреднённые метрики (уровень DC, внутриблочная детализация) совпадают с эталоном.  
  Обычный deblock её не берёт, потому что дело не в силе шва, а в самой регулярности перехода между разнородными представлениями. Этот фильтр — единственная подтверждённая рабочая техника против такой решётки; она пока существует только как программная модель, а не как реализация в реальном GPU-шейдере читалки.

## Энтропийное кодирование

Финально закодированные потоки данных сжимаются **brotli** (не zstd — тот стабильно хуже по весу и медленнее).

Внутри brotli отдельно потюнены параметры под характер данных кодека:

- без словаря,
- с урезанным числом кандидатов при сборке блоков и гистограмм,
- с кэшированием одной из внутренних оценок стоимости.

Эти правки дают речь именно про **скорость при неизменном весе**, поэтому не относятся к весовой части.

Контекстное моделирование энтропии (что обычно даёт выигрыш по весу, но стоит времени) применяется избирательно — не на всех потоках подряд, а только на тех типах данных, которые реально несут основную часть весовой пользы от такого моделирования; на мелких/маловажных потоках оно того не стоит.

## Что выброшено и почему (архитектура/качество)

- **Последовательное предсказание пикселей (JLS/MED, «CPU-путь»)** — при равном качестве даёт заметно меньший вес, чем вся текущая архитектура. Отклонено безоговорочно: по конструкции каждый пиксель зависит от уже восстановленных соседей, что делает декодирование строго последовательным — а значит, требует CPU, а не GPU-шейдера. Это нарушает требование проекта.
- **Векторизация в любой форме** (полный контур, отдельный слой для линий, предиктор на основе кривых) — многократно проверена и отклонена. Скринтон распадается на сотни тысяч крошечных фигур (точки, сглаженные края), что делает векторное представление тяжелее и хуже растрового. Даже на заведомо лучшем для вектора содержимом (чистые длинные линии манхвы) простая растровая маска с обычным сжатием оказывается втрое дешевле параметрической кривой — потому что тонкая линия имеет двойной периметр контура, за который параметрическое представление вынуждено платить.
- **Параметрическая регенерация полутонового растра** (детерминированное восстановление сетки точек по параметрам вместо хранения самих точек) — скан манги недостаточно регулярен (шум сканирования разрушает фазу решётки), регенерация по фазе даёт видимый муар.
- **Синтез процедурного шума вместо хранения скринтона** — даёт визуальный мусор: скринтон несёт реальную тональную информацию (плотность точек = воспринимаемая серость), а не декоративную текстуру, поэтому его нельзя заменить произвольным шумом.
- **Пирамидальное (многоразрешенческое) предсказание как GPU-native альтернатива последовательному предиктору** — измерено и отклонено: билинейное предсказание с половинного разрешения теряет мелкий скринтон целиком и даёт ореолы на краях, проигрывая по всем показателям.
- **MRC/билевел** (фон + чёрно-белая маска + размытие для сглаживания) — сглаживание маски убивает тонкие штрихи текста (антиалиасинг в 1–2 пикселя ширины схлопывается в серое пятно, а без суперсэмплинга восстановить его нельзя).
- **Адаптивный 4×4-DCT (последняя из «техник WebP»)** — изолированный тест обещал заметный выигрыш, но в реальной системе оказался хуже: при смене базиса меняется контекст предсказания соседних блоков, и доминирующий поток остатка растёт сильнее, чем DCT экономит.
- **Дизер (Bayer) на цвете** — визуально даёт заметный цветной шум, отклонён по результатам живого просмотра.
- **Постфильтр «привязка к реальной палитре»** (снап рекона к ближайшему настоящему цвету изображения) — не решает жалобу пользователя: артефакт был не в «придуманных» цветах, а в смещении реально существующих цветов не туда, куда нужно — постфильтр лечит другую проблему.
- **Небольшая переклассификация «тёмных гладких» блоков по критерию яркости** — снижает вес, но не убирает решётку швов (проблема в разнородности режимов, а не в конкретном пороге классификации).
- **Полная перестройка каскадного классификатора блоков в единый rate-distortion-оптимальный выбор** — начата, но не завершена; текущий классификатор — исторически сложившийся каскад условий, санкционированный к переработке, но решение проблемы швов найдено не через это, а через loop-filter.

## Вес: откуда он берётся и что с ним сделано

### Куда уходят байты

На типичной странице манги основную долю веса несёт не карта режимов и не индексы словаря, а **квантованный остаток** (разница между предсказанием любого рода и настоящими пикселями) — он один способен занимать почти половину всего веса блока люмы.

DCT-коэффициенты, coverage, VQ-индексы, IBC-смещения, служебные метаданные и intra-режимы вместе составляют существенно меньшую долю.

Вывод: борьба за вес почти всегда идёт вокруг того, как **дешевле упаковать** и как **реже понадобиться** остатку, а не вокруг экзотики в самих режимах.

### Что взято ради веса

- **Частотный словарь (не k-means) для VQ** — не просто быстрее в 2000 раз, но и даёт лучшее качество на бит, потому что попадает в реальные повторяющиеся блоки, а не в их усреднение.
- **Чистка палитры препроцессом** (снятие редких цветов к ближайшему часто встречающемуся) для манги — снижает энтропию для любого последующего кодирования практически бесплатно; для манхвы применяется осторожнее (у неё меньше запас по искажению без видимой потери).
- **Компактная упаковка потоков остатка**: разделение на битовую маску «где есть ненулевые значения» + отдельное компактное хранение самих ненулевых значений (вместо равномерного хранения всех, включая нули) — экономит одновременно и вес, и время сжатия, потому что подаваемый на вход энтропийному кодеру поток становится короче и однороднее.
- **Избирательное контекстное моделирование энтропии** — включено только на тех типах потоков (картах режимов, параметрах плоскостей и т.п.), которые реально несут основную весовую пользу; на масках и мелких служебных потоках оно того не стоит и почти не меняет вес, лишь замедляет.
- **Квадродерево для хромы** (переменный размер листа: крупный на гладком цвете, мелкий на резкой границе) — даёт кратное снижение веса цветовой составляющей при том же качестве, потому что не тратит биты на детализацию там, где цвет и так гладкий.
- **Разные наборы порогов и режимов для манги и манхвы** — единый профиль на два принципиально разных типа контента (чёрно-белый печатный скан против цветного цифрового рисунка) оказался не оптимален: у манхвы, например, часть манговых режимов (агрессивный DCT, coverage) только вредит на чистом цифровом искусстве — раздельные профили с разными квантовыми лестницами снижают вес там, где общий профиль был компромиссом.
- **Random-access полосами вместо словаря или блока как атома доступа** — позволяет читалке декодировать часть страницы без веса, добавляемого самим механизмом произвольного доступа. Единственная цена — независимое сжатие каждой полосы теряет часть межполосной избыточности; это и есть единственный «налог» на random-access в системе.

### Что выброшено по весовым причинам

- **Увеличение словаря VQ до очень больших размеров на главу** — не работает: индекс растёт быстрее, чем падает остаток, потому что содержательная часть манга-страницы в основном уникальна и не повторяется даже в очень большом словаре.
- **«Сырое» (не заблокированное) хранение хромы** ради устранения квадратов на цвете — устраняло артефакт, но раздувало вес примерно на четверть; проблема решена бесплатно другим способом — целевым фильтром на декодере.
- **CABAC / адаптивный арифметический кодер / rANS вместо brotli** — теоретически способны приблизиться к энтропийному пределу чуть ближе (зазор всего в несколько процентов), но эти методы по конструкции строго последовательны на декодировании — тот же конфликт с требованием «ноль CPU на пиксель», что и с последовательным предсказанием. Отклонены по этой причине, а не из-за недостаточного выигрыша в весе.
- **zstd вместо brotli** — стабильно проигрывает brotli и по весу, и по скорости на данных этого кодека.
- **Наращивание глубины/окна поиска совпадений** и другие «более честные» настройки энтропийного кодера сверх определённого порога — данные кодека содержат мало и коротких повторов, поэтому такие рычаги (глубина дерева поиска, лимит числа кандидатов-совпадений) практически не работают. Эффективны только принудительное урезание длинных редких совпадений и уменьшение числа кандидатов при построении гистограмм; остальное — шум.
